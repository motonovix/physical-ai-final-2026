# 動画の作り方

提出物の 1 つ、YouTube 動画の素材づくりと書き出しのメモ。
素材の動画と書き出した動画は重いので Git に入れない（`assets/`・`build/`・`local.mk` は `.gitignore` 済み）。

## 構成（案）

提出の条件は **1 分以上 3 分以内**。約 2 分を目安にする。
テーマは「ゲームコントローラを使った MacBook でのテレオペ」。題名は **ゲームコントローラと MacBook で始める フィジカル AI**、
副題は「LIBERO のロボットをテレオペしてデモを集め、VLA を追加学習する」（2026-10-19 決定）。
前半は Mac で teleop を動かしている様子の画面録画、後半は parc2026 で追加学習したモデルがタスクを解く動画。

### 話すときに押さえる事実

学習と評価は、すべて別の非公開リポジトリ（parc2026、PARC2026 コンペ用）で行った。後半はそのとき撮った動画を使う。
このリポジトリの teleop・データセット化・notebook は、parc2026 で実際に使ったコードを提出用にまとめたもので、
このリポジトリのコードで学習し直してはいない。

- **SmolVLA（後半 1）**
  - 初期重み `lerobot/smolvla_libero_plus` に、人が teleop で解いた 18 本（赤いマグの課題、1,942 frame）で LoRA（r16）を 1,000 step 当てた。
    このリポジトリの ①→②→③ と同じ流れ。
  - 評価は、学習に使った初期配置での 1 試行。未知の配置への汎化を示すものではない。
  - 同じ重みを、シミュレータの版などの条件を変えて動かした別の 2 試行は、時間内にゴールに届いていない。
- **π0.5（後半 2〜4）**
  - 動画内の表記は「π0.5」にそろえ、VLADrop の名前は出さない。
    実体は、π0.5 を LIBERO-Plus で学習し、言語モデルの層を 9 つ落とした軽量版（VLADrop の Drop9）が起点。
    これを、元の LIBERO の課題を逆向きにした課題の教師データ（415 episode）で 600 step 追加学習した。
  - 評価は、逆向きの課題 8 種 × 指示文 2 通り（原文・言い換え）の 16 問、各 1 試行。学習と評価の初期配置が重なる。
  - 成功は BDDL のゴール条件の成立。「ほかの物を動かさずに」は、対象外の物体が 1 mm 以上動いていないこと。
- **話す前に確かめること：** π0.5 の教師データ 415 本を、人の teleop からどう作ったか。parc2026 の記録で確かめる。

## 前半：teleop の画面を録る

Mac で teleop を動かしている様子を、画面録画で動画にする。学習用のデータを集めるための操作ではない。

### 撮る素材

| 素材 | 中身 | 本数 | 1 本の長さ（生） | 使う長さ |
| :--- | :--- | :--- | :--- | :--- |
| **A（必須）** | teleop を起動し、課題を選んで、READY の画面から動かし始めるまで | 1〜2 本 | 20〜40 秒 | 10〜15 秒 |
| **B（必須）** | 「ボウルをコンロに載せる」を最初から最後まで解く。ゴール → 成功の表示 → 保存まで切らずに撮る | 3 テイク（一番きれいなものを使う） | 30〜90 秒 | 25〜40 秒 |
| C（任意） | 失敗の例。ボウルでワインの瓶を倒すなど、ほかの物を動かして判定に引っかかるところ | 1〜2 本 | 10〜30 秒 | 5〜10 秒 |
| D（任意） | 2 つ目の課題（例：ボウルを戸棚の上に載せる。後半 8 の 2 つ目の例とほぼ逆向き） | 1〜2 本 | 30〜90 秒 | 10〜15 秒 |
| **E（写真）** | Switch Pro コントローラと、teleop を映した MacBook を一緒に写した写真（横向き） | 1 枚 | — | 3 秒 |
| **F（写真）** | Switch Pro コントローラを真上から撮った写真（`assets/photo/controller.jpg`） | 1 枚 | — | 8 秒 |

必須は A と B の 2 種類（テイクを含めて 4〜5 本）。時間が余れば C か D を足す。

写真 E は `assets/photo/setup.jpg`（iPhone の `.heic` でもよい。名前は clips.json の `photo.src` に合わせる）に置き、
`make parts PART=photo` で `photo.mp4` にして、timeline.txt の `photo.mp4` の行の `#` を外す。
横向きで撮り、画面には teleop を映しておく。名前のシールや通知、顔の映り込みなど、個人につながるものが入らないようにする。
画面録画とは別に、Pro コントローラを持つ手元を iPhone で 10〜20 秒撮っておくと、画面の隅に重ねたり、つなぎに使ったりできる（任意）。

### 課題の選び方

LIBERO-Plus の課題は、どれも元の課題にカメラ・照明・背景・初期姿勢などの揺らぎを足した変種になっている。
「ボウルをコンロに載せる」の変種は次で一覧できる。揺らぎの小さい L1 のものから、見た目が後半の台所に近いものを選ぶ。

```bash
make -C teleop list SUITE=libero_goal FILTER=put_the_bowl_on_the_stove
make -C teleop teleop SUITE=libero_goal TASK=<番号>
```

### 撮り方

1. teleop を起動し（`make -C teleop teleop`、[teleop/README.md](../../teleop/README.md)）、窓を大きめにしておく。
2. `⌘⇧5` で「選択部分を収録」を選び、teleop の窓だけを囲んで収録する。
3. 撮った `.mov` を `assets/teleop/` に置き（例 `a2.mov`・`b2.mov`）、[clips.json](clips.json) の `screens` に
   元の録画・使う範囲（秒）・見出しを書いて `make parts` する。窓の範囲は黒い余白から自動で切り出し、元の音声は外す。
   テロップは `captions` に、出す時刻 `from`・消す時刻 `to`（秒、パーツの頭から。省略すると最後まで）と文言を書く。
   文言の中の改行（JSON の `\n`）はそこで行を変える。

2026-10-19 に撮ったもの：A は 2 本（a1・a2）、B は 2 本（b1・b2）。a2 のメニュー部分を A、b2 を B、
ワインの瓶に当たった b1 を C に使った。a1・a2 は操作画面に切り替わると窓が広がって右端が枠から切れるので、メニューの部分だけを使う。

- ナレーションは後から別に録って重ねるほうが、撮り直しが楽。収録中はマイクを切っておく。
- B は何度か練習してから撮ると、迷いのない動きになって見やすい。途中で一時停止しない。
- 画面録画がカクつくなど画質が足りないときは、teleop の記録（`.npz`）から同じ動きを描き直せる
  （`make -C teleop render REC=<suite>/normal/<dir>/<name>.npz FLAGS="--size 720"`。画面のガイド表示は入らない）。

### 映り込みに気をつける

- 集中モードで通知を止める。
- ターミナル（プロンプトにユーザー名やパスが出る）、Finder、メニューバーを映さない。「選択部分を収録」で窓だけを撮る。
- Omnicampus の ID を含め、名前につながる情報を映さない。

## 手順

`report/video/` で実行する。Pillow を使うので、teleop の `.venv`（`make -C teleop setup`）が要る。

```bash
cp local.mk.example local.mk   # 元動画の場所を書く（初回だけ。local.mk は Git 管理外）
make collect                   # parc2026 の元動画を assets/parc2026/ へ写す（SSD をつないで、初回だけ）
make parts                     # パーツを作る（PART=teleop_b で 1 つだけ。画面録画は clips.json の screens）
make norm                      # 見出しを付けずに、assets/teleop/ の録画をそのまま 1920x1080・30fps にそろえる（任意）
make sheet                     # パーツのコマを並べた確認用の画像（build/sheet/）
make final                     # timeline.txt の順につなぐ → build/final.mp4
make open                      # 見る
```

`make collect` の後は SSD が無くても作り直せる。

### 書き出しの形式

YouTube の推奨に合わせ、すべてのパーツを同じ形式にそろえてからつなぐ。

| 項目 | 値 |
| :--- | :--- |
| 映像 | 1920x1080・30fps・H.264 High・CRF 18・yuv420p |
| 音声 | AAC・48 kHz・ステレオ・192 kbps（音の無いパーツには無音を入れる） |
| その他 | `+faststart`（先頭から再生を始められる） |

元動画は 256px（SmolVLA は 512x256）なので、拡大すると少し粗い。

### 文字の入れ方

コードの画面（`code.mp4`）だけは、notebook のセルを pygments で色付けした HTML にし、Chrome（headless）で画像にしている。
抜き出すセルと行は clips.json の `code.cells`（セルの番号と、`from`・`to` に含まれる文字列）で決める。

この Mac の ffmpeg には文字を描く機能（drawtext・subtitles）が入っていない。
見出しや「成功」の札は Pillow（ヒラギノ角ゴシック）で画像にして重ねている（[scripts/build_parts.py](scripts/build_parts.py)）。

## ナレーション

台本は [clips.json](clips.json) の `narration.lines` に、パーツの名前（`teleop_b` など）ごとに書く。
`make final` で、場面ごとに読み上げの音声を作り、その場面に重ねる。台本や設定を変えた場面だけ作り直す。

読み上げは `narration.engine` で選ぶ。

- **`say`：** Mac の読み上げ。声は `narration.say.voice`（既定 Kyoko）。
- **`aivisspeech`：** [AivisSpeech](https://aivis-project.com/speech/)（無料・手元で動く）。アプリを起動しておくと、
  `127.0.0.1:10101` の API（VOICEVOX 互換の `/audio_query` → `/synthesis`）で読み上げる。
  声は `narration.aivisspeech.speaker` に style ID を書く（`make voices` で一覧。空なら最初の声）。
  `speedScale`・`intonationScale`・`tempoDynamicsScale` なども同じ所に書ける。
  使う声のモデルの利用規約（クレジット表記の要否）を確かめる。

- **自分の声に差し替える：** `assets/narration/<パーツの名前>.m4a`（`.wav`・`.aiff`・`.mp3` も可）を置くと、その場面だけ読み上げの代わりに使う。
  ほかの場面は読み上げのまま。QuickTime の「新規オーディオ収録」や iPhone のボイスメモで録ればよい。
- **長さ：** ナレーションは場面の頭から 0.4 秒後に始まる。ナレーションが場面より長いときは、最後のコマで止めたまま延ばす（終わりに 0.6 秒の余白）。
- **読み方：** 読み上げが読み違える語は `narration.readings` で読み方に置き換える（例 `π0.5` → 「パイゼロ テンゴ」）。画面の文字は変わらない。
- **音量：** 場面ごとに -16 LUFS にそろえる。
- ナレーションなしで書き出すときは `make final NARRATION=0`。

2026-10-19 時点は AivisSpeech の「まお / おちつき」（style ID 888753763）で、全体は 2 分 13 秒。
声のモデル（まお・コハク）は Aivis Common Model License 1.0 で、営利・非営利とも使え、クレジット表記は任意
（入れるなら「AivisSpeech: まお」）。Mac の読み上げに戻すなら `narration.engine` を `say` にする。

無音の間は無音の間は、冒頭のタイトル、失敗の例の後（約 2 秒）、
解けた例の後半（約 5 秒）、最後の締め。

## 仕上げ

- **ナレーション・BGM：** iMovie などで `build/final.mp4` に重ねるのが早い。仮の読み上げは `say -v Kyoko -o narration.aiff "..."` で作れる。
- **アップロード：** YouTube へは自分のアカウントで上げる。公開範囲（限定公開など）は課題の指示に合わせる。
